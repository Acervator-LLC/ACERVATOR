## 1. The platform reports the operator's whole chain as altered

### The altered-chain alarm, as the program printed it

```
acervator.local_testnet chain NOT verified: 3135 of 3136 blocks altered
[1, 2, 3, 4, 5], 0 parent links broken [], 3135 of 3135 transactions altered
['0x3f79536e53815466', '0x7f07bcdd3c90178a', '0xf846e86ef22bf18f',
 '0x232e4219499333ad', '0x0dddbf117ff46bfd']
```

`LocalTestnet.verify_integrity` returned `is_verified` false on every record except
genesis. The load itself succeeded: `get_competition_stats` reported 3,135 blocks,
3,135 transactions and 2,565 events.

### Reproducing the altered-chain alarm

The shared reproduction above, phase `confirm`. The alarm appears twice, once from
inside `_try_load` and once from the explicit call that follows it.

### Why the alarm fires

The stored id of a record is not the id its own fields produce.

```
stored block 1 hash   0xbc0047e11ff7d701b6729d2b14e57a4823c878162e4d214dfdbf0f0ffe9a1c12
recomputed block 1    0xef257af694dadf5fb42f8de41163013396eda69d6318993b8f774dd6c4f6349f
```

His file predates records taking the hash of their own contents as a name, and
`SCHEMA_VERSION` stayed at 1 when that landed. `_try_load` therefore accepts the
file and every record reads as tampered.

### Why the alarm is not corrected here

Both available repairs change what the integrity figure means and both touch
operator data.

```
raise SCHEMA_VERSION   _try_load unlinks the file, destroying 3,136 blocks of his
                       own history
re-assign ids on load  a tamper check rewriting the ids it checks is the one thing
                       it must never do
```

The choice between keeping the existing history unverifiable and starting the chain
again belongs to the operator. It needs its own unit once he rules.

### The alarm on rerun

Unchanged, and deliberately so. The state rebuilds correctly from the file, so the
replay premise this unit measures holds; only verification of the pre-addressing
records fails.

## 2. The re-save is 112,884 bytes smaller than the file it loaded

### The missing bytes, as the file system reported them

```
U32 operator_chain_bytes_on_disk = 4059629
U32 resave_indent2_bytes = 3946745
```

A save path that loses 2.8 per cent of a file it just read is a data loss until
proved otherwise, and the per-record figures for this whole unit rest on which of
the two numbers is the content size.

### Reproducing the missing bytes

The shared reproduction above, phase `confirm`, then comparing the two files.

### Where the bytes went

No content is lost. Every section is byte-identical, and the whole difference is
the line terminator.

```
sections that differ        none
his file        112,885 CRLF endings, 0 bare LF
the re-save           0 CRLF endings, 112,885 bare LF
112,885 - 1 carriage returns = 112,884 bytes
```

An older build wrote the file in Windows text mode, which turns one newline into
two bytes. `atomic_write_text` states that it performs no newline translation, so
the current writer emits one byte a line.

### What changed instead of the writer

No code change. The current writer is already right and the next save of his chain
will shrink the file by 112,884 bytes without changing a record.

The figures in the engineering note carry the correction instead. The per-record
averages previously recorded for this tab divide by 4,059,629, which includes the
carriage returns, so they run 2.86 per cent high and correct to 283, 359 and 313
bytes.

### The content size on rerun

```
U32 base_indent2_bytes = 3946745           phase action
U32 batch_base_indent2_bytes = 3946744     phase batch, saved_at one digit shorter
```

The same value on two independent runs, one byte apart from a float's length. Every
per-action figure in this unit is a difference against it.

## 3. The field the world-turn rule orders by is the one field no id covers

### The ordering gap, and why no exception marks it

No exception. The defect is a disagreement between two correct designs, and running
the chain is what makes it concrete: two nodes can hold one transaction with
different timestamps and both chains verify.

### Reproducing the ordering gap

Read what each id function covers, then drive the chain and read a record back.

```
block_id        number, parent_hash, timestamp, transactions
transaction_id  from_addr, to_addr, function_name, args, gas_used, status
```

`TxRecord` carries a `timestamp`, and `transaction_id` excludes it on purpose so
that two nodes agree on an id.

### Why the gap exists

The exclusion is correct for agreement and wrong for ordering, and the world-turn
rule orders sequentially by timestamp when the block closes. One field cannot be
both excluded for agreement and relied on for order.

### The direction recommended for the ordering gap

Not built here, by instruction. The recommendation is for the block to assign each
transaction its position at close and for that position to enter `transaction_id`.
The block already holds its transactions as an ordered list and `block_id` already
covers that list, so the position exists and needs only to become part of the
record's identity.

```
submitter's timestamp in the id   rejected: a node can backdate its own action
block timestamp orders all        rejected: sub-block order is what the rule needs
position assigned at close        recommended
```

### What the ordering gap costs the ceiling

Nothing to rerun. The change does not move the byte ceiling: a position field costs
about ten bytes against 399, inside the rounding already taken. It alters every id
on the chain, so it is a schema change and needs its own unit.
