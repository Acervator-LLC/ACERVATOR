## Pre-mortem - does a derived figure reproduce exactly?

Run before the module existed, as a scratch script over the bare arithmetic. The
design sentence under attack: a leg's progress is a function of the opening turn,
the current turn, the rate and the two end points, and two reads of one leg must
agree to the digit.

The `decimal` module computes a square root to the precision of the **ambient**
context, which any other code in the process may change. A leg length is a square
root, so the ambient setting could have moved a derived position.

```
length of a 300 by 400 step span, ambient precision 28   500
the same span, ambient precision 4                       500
the same span, ambient precision 60                      500
an irrational case, 100 by 100, ambient precision 28     141.4213562373095048801688724
the same, ambient precision 5                            141.4213562373095048801688724
```

The fix that the pre-mortem settled, before a line of the module was written: every
derived figure is computed inside `decimal.localcontext()` at
`MOVEMENT_PRECISION`, which is the `decimal` module's own default of 28. The
ambient setting cannot reach it.

The same run found a zero-span leg raising `InvalidOperation` from a division by a
zero length, which is why `leg_length_steps` refuses a span of no step at write
time rather than guarding the division at read time.

```
a leg spanning no step   MovementError: a leg spanning no step is not a leg
```

## Error one - the handover turn reported no movement

### The handover turn in the driver output

A journey crossed a terrain border on turn 4. Leg 0 ran on open ground and arrived
on turn 4; leg 1 opened on turn 4 in marsh. Reading turn 4 reported that the mover
had covered nothing.

```
turn 4: leg 1 zone marsh this turn 0%
turn 5: leg 1 zone marsh this turn 40.0%
turn 9: leg 1 zone marsh this turn 40.0%
```

The mover did move during turn 4. It covered the last 100 steps of leg 0, and the
figure a consumer reads said zero.

### Reproducing the handover turn

```
python -X dev -X faulthandler U40_drive.py
```

with `PYTHONWARNINGS=error`, under the section headed
`a journey crossing the zone border becomes two legs`. The driver opens leg 0 on
turn 0, opens leg 1 on `leg.arrival_turn`, and prints `square_pct_this_turn` at
turns 4, 5 and 9.

### The cause of the handover turn

`WorldJourneys.leg_covering` selected the last leg whose `opened_turn` was at or
before the requested turn. On the handover turn both legs qualify and the later one
won. A leg that opens on a turn has not moved under it yet, because the mover is
standing at that leg's own start point, so `progress_at` returned an elapsed count
of zero.

### Correcting the handover turn

`leg_covering` now selects the last leg whose `opened_turn` is strictly before the
turn, and falls back to the first leg only when the turn is the journey's own
opening turn.

```python
moving = [leg for leg in held if leg.opened_turn < turn]
if moving:
    return moving[-1]
if turn == held[0].opened_turn:
    return held[0]
```

This is the cause and not a symptom: the two legs share one point in space, so
reading the handover turn from leg 0 gives the same position leg 1 starts from, and
the per-turn figure is the one leg 0 actually covered.

### The handover turn rerun

```
turn 4: leg 0 zone plain this turn 100%
turn 5: leg 1 zone marsh this turn 40.0%
turn 9: leg 1 zone marsh this turn 40.0%
```

## Error two - a leg was accepted that left the zone it named

### The out-of-zone leg in the driver output

The refusal list drove a leg from inside the `plain` region to a point four squares
beyond its far border, naming `plain` as its terrain. It was accepted.

```
a leg leaving its zone: NOT REFUSED
```

### Reproducing the out-of-zone leg

```
python -X dev -X faulthandler U40_drive.py
```

under the section headed `refusals`. The leg runs from `(400, 500)` steps to
`(1199, 500)` steps while `plain` spans squares 4 through 7 in both axes.

### The cause of the accepted out-of-zone leg

`open_leg` checked only that the region held the leg's **midpoint**. The midpoint of
that leg is at 7.995 squares in x, which is inside `plain`. A long enough leg keeps
its midpoint inside a region while both the leg and its end point leave it, so one
point test cannot decide containment.

### Correcting the out-of-zone check

`_require_zone_covers_leg` now applies two checks, both using geometry the grid
already carries. Each end point must sit in a square the zone's own
`squares_in_extent` covers, and the midpoint must sit inside the boundary under
`ZoneRegion.holds`. No second geometry was written and no division was added to
`holds`.

```python
extent = zone.squares_in_extent(width)
for step_x, step_y in ((from_x, from_y), (to_x, to_y)):
    end = position_at_steps(step_x, step_y, width)
    if end.square_index not in extent:
        raise MovementError(...)
```

What the pair does not decide is stated in the method's docstring and in the
manual: a region that bends back on itself, where a straight leg leaves and
re-enters while staying inside the zone's own squares.

### The out-of-zone rerun

```
a leg leaving its zone: MovementError: zone plain does not cover square 141 at
(1199, 500) steps; a leg ends at the zone's border
```

## Error three - the TA archetype refused the containment check

### The finding

```
ta-quant TA004 high
units mismatch: 'square' (dimensionless) compared against 'extent' (absolute).
```

`passed=false`, exit 0. The verdict was read out of the JSON, not from the exit
code, because `ta_archetype` exits 0 on a `passed=false` file.

### Reproducing the TA004 finding

```
python -m dev_harness.harness.ta_archetype src/competition/world_movement.py
```

### The cause of the TA004 finding

The first version of `_require_zone_covers_leg` computed its own square index:

```python
square = square_index(step_x // STEPS_PER_SQUARE, step_y // STEPS_PER_SQUARE, width)
if square not in extent:
```

The floor division marked `square` as a dimensionless quantity, and it was then
compared against a collection of absolute square indices. The rule is reading a
real confusion: the step-to-square conversion existed in two places, once in
`position_at_steps` and once here, and only one of them owned the units.

### Correcting the TA004 finding

The duplicate conversion was deleted. `_require_zone_covers_leg` now calls
`position_at_steps`, which already owns that conversion, and compares the
`square_index` it returns against the extent. One place converts steps to squares.

### The TA004 rerun

```

findings              []
tool_availability     ta-quant ok, ta-chart ok, ruff ok
errors                []

```

## What one record a leg costs, measured

Every figure is the size of the file the chain wrote, reported by the file system,
with the chain driven through the real install path. Each condition ran in its own
directory and the difference was divided by the 655 legs driven.

```
install, a world, a layer, a zone, a terrain rate, no leg   4,237
one leg                                                     5,535
655 legs, the path open_leg runs                          858,818
655 legs, packed argument, one block a turn                317,568
655 events on one leg's record                            281,655
```

Subtracting gives the per-record cost.

```
one leg as open_leg writes it     1,305 bytes
its event alone                     422
its block and transaction           883
packed argument, one block a turn   478
```

Two conditions ran twice. The figures moved by fractions of a byte, because a
transaction carries a timestamp rounded to three decimal places and a trailing zero
is one character shorter.

```
655 legs, named, run one    858,779      run two   858,818
655 legs, packed, run one   318,080      run two   317,568
```

### The two figures the design quoted, re-measured

The design quoted 1,015 bytes for the current encoding and 399 for a compact one,
at 655 participants against a budget of one megabyte a layer a world turn. The
arithmetic behind those two totals reproduces exactly, which confirms that the
megabyte is read as 1,048,576 bytes.

```
655 x 1,015   664,825 bytes   63.4% of 1,048,576
655 x   399   261,345         24.9%
```

The per-record figures do not reproduce, and both are now larger. The save path
changed to a running log that names every record by the content id of its own
fields, which adds bytes to every record, and `open_leg` emits an event as every
other record in this package does.

```
quoted 1,015 bytes   measured 1,305    81.5% of a layer's turn budget
quoted   399 bytes   measured   478    29.9%
```

The design's conclusion is strengthened. Writing each mover's progress every turn
would take 81.5 per cent of a layer's entire turn budget for one turn of walking,
where the earlier figure said 63.4.

### One record a leg against one a turn

Three journeys were driven across one terrain region, of three, six and
twenty-four turns. The chain reports its own transaction count.

```
walk of  3 turns   1 record on the chain    3 progress figures read
walk of  6 turns   1                        6
walk of 24 turns   1                       24
three journeys     3 transactions added to the chain
```

At 655 movers on one twenty-four turn journey the cost is 854,581 bytes once
rather than each turn, which is 35,607 bytes a turn, 3.4 per cent of the budget.

## What sets a rate, and what is left as a seam

```
the base      BASE_STEPS_PER_TURN, one square a world turn. Settled by his own
              wording: a one-hour turn and an hour's walk a square agree with no
              adjustment.
terrain       registered per zone through set_terrain_rate. No default, no value
              chosen here, and a zone with none refuses to carry a leg.
encumbrance   given when the leg opens. No default and no upper bound.
```

Nothing in `src/competition/` holds what a mover carries. `loot_drop.py` holds
rarity weights, which are drop odds and not a load, and no module holds an
inventory or an equipped set. Whatever supplies a mover's load will also bound the
multiplier, and no such module exists.

The kilometre label reaches no arithmetic. No distance in kilometres appears in
the new module, and no rate reads one. The issue records that the travel rates
behind those labels are unsourced.
